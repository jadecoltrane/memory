# 目标不是会写,是看得懂改了什么

这条路径的验收标准不是"能自己写脚本",是**能读懂一次改动、并且判断出对方说得对不对**。这两件事的门槛差一个数量级:写代码要记住语法、要 debug、要设计;读代码只要认得出结构和意图。而且被动的坑几乎全出在"看不懂所以只能信"这一步。

按顺序学,别跳。前面的是后面的地基。

## 一、Git 的心智模型(最重要,先学这个)

整个记忆库就架在 git 上——归档是改名、找回删掉的东西是翻历史、笔记能改一百遍不怕改坏,全靠它。

**别从背命令开始,先建立一个正确的图像**:git 存的是**一系列快照**,不是"改动记录";分支只是一个指向某个快照的标签;合并就是把两条线的快照合到一起。想通这一点,大部分命令自己就解释得通了。

库里已经有一篇 [[Notes/知识/Git核心原理与Obsidian-Git操作速查|Git核心原理与Obsidian-Git操作速查]],那篇是命令速查、补的是「怎么做」;这一节补的是「为什么这么做」,两篇配着看。

推荐 [Learn Git Branching](https://learngitbranching.js.org/?locale=zh_CN)——浏览器里画出来的交互式教程,有中文,每一步都能看见提交树怎么变。**只做前两章就够用**,后面的 rebase、cherry-pick 现在用不上。

学完应该能看懂的:
- 为什么"三方合并不报冲突"反而是危险的(两边改了不同地方,git 觉得自己处理得很好)
- `git show <commit>^:<路径>` 为什么能把删掉的文件原样拿回来
- 为什么归档用 `git mv` 而不是删了再建(改名保住了历史)

## 二、Markdown + YAML frontmatter(半小时)

笔记开头 `---` 之间那一段就是 frontmatter,格式叫 YAML。要认的只有:`键: 值`、列表写成 `[a, b]`、缩进有意义(空格数量不能乱)。

**为什么值得单独学半小时**:库里所有自动化都在读这几行——`tier` 决定分层,`expires` 决定到期提醒,`published` 决定发布状态。缩进错一格,脚本就读不到,而且不会报错,只会当它不存在。

## 三、命令行(只学十个)

`cd` `ls` `cat` `head` `grep` `find` `python3` `git` `mv` `rm`。够了。真正要建立的直觉是:**命令行是一层一层套的**——`|` 把前一个的输出喂给后一个。看懂 `git log --oneline | head -5` 是"列出提交,只要前五行",就算过关。

## 四、Python:只学到能读(不用会写)

推荐 [Automate the Boring Stuff with Python](https://automatetheboringstuff.com/)(免费在线全文),**只看前 6 章**:变量、列表、字典、if/for、函数。跳过所有练习项目。

目标是打开 `Meta/scripts/` 里任何一个脚本,能说出这一段在干什么。比如看到

```python
for p in sorted((ROOT / "Notes").rglob("*.md")):
```

能读成"把 Notes 下所有 .md 文件按名字排序,一个一个过"。这就够了。

**正则表达式**(`re.compile(r"...")` 那种)单独列一句:先别学,遇到了问就行。它的学习曲线陡而回报窄。

## 五、CSS:只学选择器和层叠

工作台那些卡片样式全是 CSS。**不用学布局**(flex/grid 那些),只要搞懂两件事:

1. **选择器**:`.workbench .callout[data-callout="ask"]` 读作"在 .workbench 里面、带 data-callout="ask" 属性的 .callout 元素"。
2. **层叠**:同一个属性被写了两遍时,谁赢?越具体的选择器越赢,`!important` 最赢。

学这两个就能看懂大部分"样式没生效"的原因。[MDN 的 CSS 选择器文档](https://developer.mozilla.org/zh-CN/docs/Web/CSS/CSS_selectors) 是中文的,查着看,不用通读。

## 六、GitHub Actions(最后学,而且只学读)

`.github/workflows/*.yml` 就是"什么时候、在哪台机器上、按顺序跑哪几条命令"。结构只有三层:`on`(什么触发)、`jobs`(几件事)、`steps`(每件事的步骤)。看懂这三个词,那几个文件就都能读了。

## 真实的坑长什么样(比教程有用)

这些都是这个库里实际发生过的,每一个都对应上面某一节:

- **中文文件名 + git**:git 默认把中文路径转义成 `"Notes/\346\200\235…"` 还带引号,于是 `startswith("Notes/")` 静默失配,检查看着在跑其实一条都没匹配上。要加 `-c core.quotepath=false`。→ 对应第一、四节
- **CSS 选择器写少了一个容器**:问题卡编号靠"数前面有几个兄弟块",但只写了阅读视图的容器 `.markdown-preview-sizer`,而默认视图是源码模式(容器叫 `.cm-sizer`),于是两张卡都显示 1。→ 对应第五节
- **三方合并不报冲突**:两期工作台的"回答区空行"文本完全相同,git 把"远端的新问题"和"本地的旧答案"当成互不相关的改动各自干净合并,结果新问题下面挂着上一期的答案。→ 对应第一节
- **哨兵靠 author 认机器人**:AI 提交的 author 和手动提交一模一样,于是它每次都自己报自己,误报把真报警淹了。判据选错了维度。→ 这条不是技术问题,是设计问题

## 怎么记进这个库

学的过程本身别整理成笔记——**教程内容不值得抄进来**,网上随时能查(见 `Meta/RESOLVER.md` 的"指针"那一类)。值得写进 `Notes/` 的只有一种:**你自己踩过、并且当时没看懂的那个坑**。那才是别处查不到的。
