# WORKBENCH — 工作台(每日生成)规范

只在处理"工作台"相关任务时读这份文件(用户点名提到工作台、要改 `工作台.md`、或跑 `daily-workbench.yml`/`weekly-gc.yml` 里涉及工作台的步骤)——**根规则文件不再内联这节内容,平时聊天不需要加载这份文件**。

根目录 `工作台.md` 是记忆库的出口:让旧记忆主动找上门,核心是提取练习而不是重读。页面固定为 **☀️ 每日回路**(`##` 标题,AI 板块)。每天由定时任务重新生成 AI 板块,其余部分(`##` 标题、所有 dataviewjs 区块——横幅、信息条、今日内容折叠壳、胶囊标签栏(笔记/概念/本周新增/最近编辑四颗点开在页面内展开面板,双链胶囊直接跳原生图谱不展开面板,➕ 新建在最右)、🎲 随机重逢卡)是固定结构或实时渲染,**生成时原样保留,永远不要改动**。

**笔记面板**点分类卡打开的是 `meta/笔记数据库.base`(Obsidian 原生 Bases,每次点开笔记面板都会重新生成,视图按 `notes/` 当前的子文件夹实时同步)——这是生成产物,不是用户笔记,不要手动编辑,也不要把它当成笔记内容去索引/复核。格式保持现有 callout 语法(`[!today]` `[!draw]` `[!seed]` `[!ask]` `[!note]` `[!write]` `[!clash]`);frontmatter 保留 `cssclasses: workbench`,但每次**必须把 `generated:` 更新为当天日期**——横幅心跳报警靠它判断每日任务是否还活着(超 48 小时未更新显红),这是"系统静默挂掉"唯一的可见信号。云端日更由 workflow 前置 sed 步骤机械写入,AI 原样保留即可;只有人工/本地更新工作台时才需要手动改这个字段。


**视觉基调**:由横幅画作在客户端用 canvas 取主色调自动算出(色相分桶投票,不用平均色——平均会把所有颜色互相抵消成灰)、写进 CSS 变量 `--wb-accent`,CSS 里再用 OKLCH 相对颜色语法派生锁定亮度的文字色/柔光底。

**🖼 每日画作**(横幅背景):每天生成时用执行器可用的网页搜索工具挑一幅著名画作(Claude 自动化使用 WebSearch/WebFetch),优先 Wikimedia Commons 上 `upload.wikimedia.org` 开头的直链图片(几百 KB 到 2MB 的中等分辨率版本,不要几十 MB 的原图),写入 frontmatter 三个字段:`painting-url`、`painting-title`(画名·作者)、`painting-intro`(一句话简介)。**链接必须是当次搜索/抓取真实确认可访问的**。选画不许与近半年重复(查重命令:`git log --since='180 days ago' --format= -p -- 工作台.md | grep '^+painting-title'`,输出仅每天一行画名,省 token 且永久封顶;不要跑裸的 `git log -p`),并在时代/地域/风格上轮换,不要连续几天同一风格。**2026-08-02 起:第一个候选验证失败(链接打不开、不是直链等)不算完事,换一幅候选继续试,最多尝试 3 幅**;3 幅都验证失败才保留前一天的值,不编造 URL——保留是最后的兜底,不是遇到第一次失败就退回的默认选项。

每日生成三个板块,都在 ☀️ 每日回路的 `[!today]+` 折叠壳里(标题留空):

- **🎴 今日抽卡**:从 `notes/` 挑"最久没被抽过"的——**优先看各篇 frontmatter 的 `last-surfaced:`,没有这个字段的排最前**(翻 git log 只作兜底,贵)。抽中之后**必须给被抽中的每篇写上 `last-surfaced: 今天日期`**(有就覆盖),这一行让下次挑选和 `gc_report.py` 都变成免费的。出 1-3 道回忆提示。**格式只有标题+问题列表,不加任何引导语**——不要加"先别点开"、"想不起来再点进去"之类的提示句,直接呈现问题本身。
- **🌱 今日延伸**:挑一个概念页(优先最近被链到的、或延伸区还空着的),补一条外部知识,标 [事实]/[推论]/[观点]、注明未联网核查;同步写进该概念页延伸区。**引用某篇笔记的录入时间时用实际日期。
- **❓ 今天的问题**:每天出**两道**独立问题(问题1、问题2),优先从概念页开放问题、或笔记间张力里出;**问题形式不限**——可以是指向用户自身经验的具体提问,也可以是纯开放式的观点/推演题,不强制绑定个人经历,两道题尽量来自不同概念/笔记,避免同质。**2026-08-02 用户反馈**:问题措辞不要堆砌概念术语、写长复杂句——用户得先在脑子里查一遍这些词/句子结构什么意思才能读懂问题本身,这已经构成理解障碍而不是引出思考;要用简单直白的口语,需要的背景直接用大白话嵌进问题正文里讲清楚,不要求用户自己代入行话或去翻概念页才能读懂题目。**页面顺序固定为两张问题卡紧挨着,不能打乱或在中间插别的块**——靠这个顺序 + 页面级卡片网格的 flex 换行,两张问题卡自动横排成一行:
  1. `[!ask]` 问题1 → `[!ask]` 问题2:标题写 `❓ 问题1`/`❓ 问题2`,内容第一段是问题正文;**紧接着先嵌套** `[!write]` 子 callout(嵌套写法:问题的引用块内再用 `> >` 包一层),标题固定 `✍️ 你的回答`,内容留 2 行空的嵌套引用行(单独一个 `> >`)给用户手写,不预设任何文字
  2. **再嵌套**一个折叠的 `[!note]-` 子 callout(同样 `> >` 写法),标题固定 `💬 我的看法`,内容是 AI 对应问题的倾向性判断,标注 [推论]/[观点],不假装客观,折叠是 honor system,展开与否交给用户自觉。**2026-07-07 二次调整:回答区要排在"我的看法"前面**——用户要求写自己的答案时不能先看到 AI 的看法,避免被提前锚定,所以顺序固定"问题正文 → 你的回答 → 我的看法(折叠)",不能颠倒。**2026-07-07 起回答区并进对应问题卡内部,不再是独立顶层卡片**(独立空卡看着像 UI 没加载完,跟问题的配对关系也读不出来),"输入井"凹陷样式由 CSS 管,生成时只管结构

**生成前必做**:读上一版每张问题卡里嵌套 `[!write]` 的回答。**按文档顺序对应**:第一个 `[!write]` 是问题1的回答,第二个是问题2的回答(2026-07-07 起嵌在问题卡内部,顺序对应关系不变)。**分别独立判断**,哪个 `[!write]` 里有内容就处理哪道:

**已知故障模式(2026-07-23、2026-07-29 各发生一次,读回答前先排查)**:手机端 Obsidian Git 插件的同步和云端 05:00 的日更之间存在竞态。如果用户答完题但还没推送到 GitHub,云端跑的时候只会看到空白框,按"未回答"跳过——这种情况问题不大,答案还在用户本地,下次打开 Obsidian 同步后能看到新一期,只是这一天没被处理,提醒用户下次尽快同步即可。**更隐蔽的一种**:用户还没推送时云端已经生成了新一期并推送;用户之后才打开 Obsidian 同步,客户端拉取远端新版本再合并本地编辑——由于"回答区两行空行"在新旧两期之间文本完全相同(都是占位空行),Git 三方合并会把"远端改过的新问题文字"和"本地改过的旧答案内容"当成互不相关的改动**各自干净合并**、不报冲突,结果是新一期的问题卡下面挂着一份答的是上一期问题的回答,读起来像是这道题被答了,实际是错行。**排查方法**:读取回答前先判断问题原文和回答内容是否语义相关;明显对不上(比如回答提到的具体情境、关键词跟当前这版问题文字对不上)就不要当成本期回答处理,去 `git log -p -- 工作台.md` 翻上一两期的问题原文比对,大概率是被合并串了行,按"补处理"流程手动核实真实对应的问题和期数,分别记录+生成碰撞(先例见 commit e6f8317 和本次 2026-07-29 的修复提交)。

1. **记录(只在值得时,取代旧的"无条件归档")**:判断这条回答值不值得留存——**只有当回答里有值得记住的判断/经历/观点/新张力**,才提炼进相关 `notes/` 笔记或概念页(按 `meta/RESOLVER.md` 的写 notes 流程 + `meta/CONCEPTS.md` 的概念规则;写 notes 时用 `type: note`、加 `source: 工作台问答`、按 checkable 规则判断、挂概念双链)。**没必要记的就不记,也不再往 `notes/问答/` 建按月归档文件**——旧回答本就留在 git 历史里,不会凭空消失
2. **碰撞(有回答时必须生成)**:在新工作台 🎴 抽卡**之前**,每道被回答的问题各插入一个 `[!clash]` callout(**默认展开,不要加折叠符 `-`**;两道都答了就两个,按问题1/2顺序排),标题 `🥊 碰撞 · 问题1 回顾`/`🥊 碰撞 · 问题2 回顾`。**2026-08-02 起固定这个四段嵌套结构(CSS 按这个结构做视觉分层,顺序和层级不能变)**:
   1. 顶层第一段是**斜体**的问题一句话概括(不加"问题:"标签,直接斜体正文)
   2. 嵌套 `> > [!write] 🗣️ 你的回答`(原文摘要,不改意,不折叠)
   3. 嵌套 `> > [!note] 💭 我的看法(上期)`(从上期折叠 callout 里搬来,完整展示,不折叠)
   4. 顶层最后一段是 `**碰撞：**` 开头的正文段——这段是全卡视觉最重的部分(CSS 给了强调色左边框+加粗),必须落在真正的分析上:指出两者的核心分歧在哪、谁的角度更贴近实际经验、哪里 AI 在偷懒或过度抽象、哪里用户可能在自我美化或回避——**不要和稀泥,不要都说有道理,要有立场**
   顶层内容只能是「第一段斜体问题」+「两个嵌套 callout」+「最后一段碰撞正文」这四块,中间不要插其他段落,CSS 的 `:first-of-type`/`:last-of-type` 选择器依赖这个顺序
